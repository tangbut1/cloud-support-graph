4. **第 4 章 系统实现**：分模块详述 JWT 与 RBAC 实现、基于 `jieba` + SQLite FTS5 的检索与拒答阈值控制、FastMCP 服务端工具实现、`AsyncSqliteSaver` 持久化与人工接管逻辑、SSE 流式与多模态处理，以及客户/坐席/评测三端界面截图。

## 3. 面试高频追问自检清单

1. **为什么不用普通 Chain 或手搓 `while` 循环，而选用 `LangGraph`？**  
   → 结合本项目转人工与高危操作审批场景，需要带状态的图持久化（`AsyncSqliteSaver`）与 `interrupt()` / `Command(resume=...)` 挂起恢复能力，且条件分支路由和防死循环步数上限在 `StateGraph` 中更可控。
2. **这里引入 `FastMCP` 的真实价值是什么？怎么防止模型越权查别人的实例？**  
   → MCP 将云资产诊断与工单读写能力从 Prompt 逻辑中解耦为标准工具契约；安全防线采用纵深防御——在 `tools_bridge` 层从经过验证的 JWT 注入 `auth_user_id`（LLM 不可见且不可指定目标用户），并在 MCP Server 内部再次校验 `instance.owner_id == auth_user_id`。
3. **如何避免大模型在不懂的问题或赔付问题上乱答乱承诺？**  
   → 前置意图守卫拦截注入与赔付诱导；知识问答走 `jieba` + FTS5 混合检索与 `RAG_MIN_SCORE` 阈值拒答；高危动作与故障建单强制挂起转人工坐席确认。
4. **为什么在 2 核 2 GiB 服务器上采用 SQLite FTS5 + 外部 Flash API，而不是本地向量模型或私有化 Dify？**  
   → 基于实际内存账（Dify Docker 官方最低要求 4 GiB 内存且启动十余个容器，2 GiB 易 OOM；本地 PyTorch 向量模型同样占满内存），采用 WAL 双库分离 + FTS5 在 <850 MB 内存内稳定运行，推理交由 `DeepSeek-V4.1-Flash-1017` API。
